VibiShowdown - Ordem atual do sistema (oficial-only)
=====================================================

Objetivo deste arquivo
----------------------
Documentar a ordem de execucao principal do app hoje:
1) ordem de rede/sincronizacao
2) ordem de processamento de turno no motor de combate


1) Ordem de rede (cliente)
--------------------------
Arquivo principal: vibishowdown/index.ts

Fluxo de inicializacao:
1. Cliente abre websocket via pacote oficial `vibinet` (src/client.ts).
2. Em on_sync:
   - watch(room, consume_network_message)
   - load(room, 0, consume_network_message)
   - post(join)
   - status muda para "synced"
   - app considera sincronizacao de tempo completa.

Fluxo de mensagem recebida (consume_network_message):
1. Deduplica por index (quando index >= 0).
2. Se mensagem for "server-managed" (assign/ready_state/participants/turn_start/state/intent_locked):
   - ativa modo server-managed
   - encaminha direto para handle_post.
3. Se ja estiver em server-managed:
   - encaminha direto para handle_post.
4. Caso contrario:
   - usa fallback cliente-deterministico (relay_consume_post)
   - reconstrui estado local a partir de join/ready/intent/forced_switch/surrender/chat.
5. Em fallback cliente-deterministico:
   - cada turno abre com deadline de 5s.
   - se algum player nao enviar intent ate o deadline, o cliente fecha o turno com fallback deterministico.

Observacao:
- Mesmo com fallback deterministico, o endpoint permanece oficial:
  wss://net.studiovibi.com
- Nao existe backend local de jogo neste repositorio.
- Nao existe protocolo custom local (`src/vibinet/*` foi removido).


2) Ordem de combate (engine)
----------------------------
Arquivo principal: src/engine.ts

Funcao central: resolve_turn(state, intents)

Ordem exata atual:
1. clone_state do estado recebido.
2. reset de flags de guard e avaliacao de mindgame de tipo no inicio do turno:
   - hierarquia: BUF > DEF > ATK > BUF
   - empate de tipo nao altera score (0 para ambos)
   - vitoria de tipo altera score individual:
     vencedor +1 / perdedor -1
   - logs gerados: `mindgame_bonus_ready` + `rps_score_update`
3. build_actions a partir dos intents.
4. Ordena fases por "order":
   - switch (0)
   - guard (1)
   - attack_01 (2)
5. Para cada fase:
   - filtra actions da fase
   - se houver duas actions, resolve iniciativa
   - executa action por action
   - regras extras de switch:
     - se o lado estiver com Arena Trap ativo, switch e bloqueado no turno valido.
     - Spikes (1 carga) dispara no proximo switch do lado alvo:
       causa 10% do sharedHpMax e e consumido.
   - se ambos os lados fizerem switch no mesmo turno:
     - aplica passivas de entrada por tipo (somente nesse caso):
       Armoth (DEF) entrando contra ATK => Arena Trap no inimigo por 1 turno
       Kairus (ATK) entrando contra BUF => Quick Punch (10 dano)
       Farien (BUF) entrando contra DEF => cura +10 HP
   - apos cada action, checa fim imediato por HP zerado
6. Fase final unica:
   - ending_turn (ordem fixa por lista interna, sem iniciativa por atributos):
     Focus Punch -> Wish -> Leech Life
7. Encerramento do turno:
   - decrement_cooldowns
   - reset_protect_flags no fim do turno
   - finalize de tiebreak de double KO (quando aplicavel)
   - checagem de limite de turnos (12 + overtime ate 5)

Regras de vida/fim de partida:
- vida e unificada por player (nao por pokemon), fixa em 200.
- se um lado chegar a 0 e o outro estiver acima de 0, a partida termina imediatamente.
- se ambos chegarem a 0 no mesmo turno:
  - ativa 1 turno extra de desempate (double KO tiebreak), com ambos resetados para 1 HP.
  - no fim desse turno de desempate: HP diferente => vencedor; HP igual => empate.
- partida base tem 12 turnos.
- no turno 12, se HP estiver diferente, vence quem tiver mais vida.
- se empatar, entram turnos extras (max 5), encerrando no primeiro turno com HP diferente.
- se continuar empatado ate o limite extra, encerra em empate.

Importante sobre passivas:
- Sistema antigo de passivas por item (`src/data/passives.ts`) continua desativado no motor.
- Todos os mons estao com passiva fixa `none` no cadastro atual.
- A feature atual usa passivas de especie ligadas no `engine.ts` (troca simultanea), sem usar o modulo legado.
- No lobby (pre-match), cada mon configura apenas 3 moves; campos de passiva/HP/EV nao aparecem.


3) Pacote inicial da feat jokenpo
---------------------------------
Mons novos:
- Armoth (DEF) - base temporaria de stats: Panda
  moves: Spikes / Recover / none
- Kairus (ATK) - base temporaria de stats: Harpy
  moves: Mega Punch / Kick / none
- Farien (BUF) - base temporaria de stats: Miren
  moves: Meditate / Ki Blast / none

Moves novos no catalogo:
- Spikes: arma hazard no lado alvo (1 carga).
- Recover: cura 20% do sharedHpMax do proprio lado.
- Mega Punch: dano flat 20.
- Kick: dano fisico escalado.
- Meditate: ATK x2 no usuario.
- Ki Blast: dano flat 20.

----------------------------------

Ordem de execucao:
- Sempre em src/engine.ts (resolve_turn e funcoes auxiliares).

Estado compartilhado:
